## 前次 TLS 记录能说明什么

前次完整安装只留下请求地址和 `curl: (28) SSL connection timeout`，没有失败连接的逐跳上下文。该记录说明当次客户端在连接预算内没有完成 SSL 连接，不能确定具体责任端点。原 Range 日志还遗漏了相对 Location 的解析，空 `REDIRECT_HOST` 不能证明没有重定向。

本机将私人域名解析到 `198.18.*` 映射；只读查询其宿主路由，接口为 `utun6`。因此无 HTTP_PROXY 环境变量也不代表绕过了虚拟隧道。但这些事实不能证明 TUN 有故障、不能定位具体出口，也不能证明宿主和 VM 使用相同物理路径。

本次未复现 TLS 超时，三组完整 GET 均成功。历史故障缺少的信息无法事后补造；其原因仍未定位，不能将它概括成私人服务不稳定，也不能用本次成功擦除历史失败。

## 可确定的 Nido 兼容性限制

独立 API 复测使用 Nido 的 `User-Agent: Nido` 和 `Accept: application/vnd.github+json`，实际协商 HTTP/2：

| 请求 | 状态 | TLS | 耗时 |
| --- | --- | --- | --- |
| 私人前缀 + 官方 `/releases/latest` API | 404 | 校验通过 | 0.994191 秒 |
| 私人前缀 + 官方 `/releases/tags/v0.8.1` API | 404 | 校验通过 | 1.371695 秒 |
| 同期官方 `/releases/latest` API 直连 | 200 | 校验通过 | 2.239664 秒 |

404 是已完成的 HTTP 响应，与握手超时无关。服务主页声明 release、archive 和文件加速，表单输入规则没有 `api.github.com`；文件代理正常与上述 API 路径不支持可以同时成立。这里确认的是**所测试的 API 路径不兼容**，没有推断其他未测试 API 入口。

已发布 v0.8.1 的自定义前缀会同时作用于 REST API、checksum 和 archive（`internal/githubdownload/download.go`）；实际旧版自更新先取 API 元数据，故在下载文件前就可能失败。`auto` 对内置文件代理已按 API/资产能力区分，自定义前缀仍缺少独立选择。这是该版 Nido 的兼容性限制，不能据此判断用户的文件代理配置错误。

v0.8.1 可用 `nido update --check --github-proxy direct --proxy <Proxy端点>` 临时绕开这一限制：`direct` 保留官方 URL，通用代理同时承载 API 和发行文件；仅添加 `--proxy` 不会取消已保存的文件前缀。此历史验证仍只说明当时的显式客户端契约。

后续按用户要求实现并纳入 **v0.8.2 的流程**为：先用文件入口安装 Nido，再用可信本地 Mihomo 包安装、配置并显式启动 Proxy，运行 `nido proxy bind download` 选择一次 listener。后续 Nido 自身、Proxy、GDS 的内部 GitHub API 自动经该入口访问官方 URL，文件资产仍用原有加速前缀，不要求用户每次指定地址。绑定保存在独立私有文件，不改主配置 schema 或全局代理，也不影响用户自己运行的 curl、Git、Conda/pip；失效时明确失败，不静默回退或自动启动。具体步骤、版本和验证边界见 [自举方案](nido-proxy-bootstrap.md)。当时的源码诊断阶段未发布、部署或修改真实服务配置，后续发行状态见本页前述链接。

该实现随后收紧为“未绑定即禁用 API”：没有 sidecar 或 listener 为空时，`api_state = disabled`，依赖 API 的版本查询、在线安装和更新在网络、候选执行、确认或写入前提示未启用，不能用 `--proxy`、`--github-proxy`、环境代理或文件前缀绕过；已有有效非空绑定后才可临时 `--proxy` 覆盖。Nido 主动查询 Codex 版本的 GitHub API 同样受该开关约束：`codex update --check` 未绑定时失败，普通 `codex update` 未绑定时跳过可选 API 预查询；官方安装/更新脚本仍保留独立代理与确认，脚本内部及 Codex 程序运行网络不变。用户显式 probe 属独立诊断。`configured` 仅为静态状态，不等于就绪；普通 status/doctor 不联网，未绑定不算 doctor 故障。本地 artifact、dry-run、无需 API 的同版本操作和不依赖 API 的文件自举脚本仍可使用。禁用规则已通过独立的 Linux amd64 隔离验收，详见[自举方案](nido-proxy-bootstrap.md#验证状态与范围)，不改写上述 v0.8.1 的历史行为和结果。

## 验收工具修复与边界

包装器在原参数前插入超时参数，会把安装器的 `-q` 移出首参数位置，破坏禁止读取 curlrc 的保证。本轮已将真实 curl 调用首参数固定为 `-q`；原 URL、协议、重定向、证书、超时和重试保持不变。后置的原生 10/180 秒仍覆盖包装器的前置 15/180 秒。

Bash 3.2 的 7 组无网络测试核验实际参数、输出保持、错误码传播和坏字节拒绝，旧命令形态被测试拒绝。旧临时 HOME/CURL_HOME 没有 curlrc，没有证据将此工具缺陷认定为历史 TLS 故障根因。真实包装器完整 GET 的当前结果单独列在上表。

相对重定向解析器也增加了有界、脱敏的离线解析与 7 项测试；原始日志保留，不打印签名查询串或代理凭据。

本轮三组成功是下载诊断，`functional_acceptance=false`，没有重新执行完整安装或原生自更新矩阵。前次真实旧包在 API 404 后的文件保护证据继续保留。未发布、部署或修改真实机器、代理服务的配置。
