# v0.8.1 Linux amd64 直链故障复查

**2026-10-19 原因复核更正：**后续宿主、Linux amd64 和验收包装器的完整文件 GET 均通过；前轮单次 TLS 超时不能归因为私人服务故障。API 路径 404 体现 Nido 统一 API/资产前缀的兼容性限制。最新证据和工具修复见 [原因复核](nido-private-proxy-diagnosis.md)，以下原始失败记录保持其当时范围。

后续修复已纳入仅面向 Linux amd64 的 [v0.8.2](nido-v0.8.2-release.md)：内部 API 可绑定具名 listener，文件资产继续原加速策略，未绑定时禁用 API。该版已发布，正式包独立验签和 API 隔离验收通过，公网分路结果另行记录；不据此重写下述旧版故障或认定历史网络原因已定位。

本次于 2026-10-18 在全新临时目录复查，只执行 Linux amd64 容器。宿主是 Apple arm64，属于 amd64 仿真，不能代替原生 Zenith-Dev 或 GPFS 验收。没有部署、发布新版本、修改真实 Conda/pip、代理、DNS 或服务配置；公开 v0.8.1 资产及标签保持不变。

## 网络与程序的区分

旧重复安装在第二次 checksum GET 收到 curl 52 空响应；旧独立自更新已取得 metadata，随后 checksum 请求连接失败。旧 Go 客户端抹去了具体传输原因，不能仅凭旧日志确定是 TLS、连接复位、上游还是转发链，也不能用此前另一轮的 API 配额耗尽解释 checksum 连接失败。

本次先运行不执行 Nido 的小文件诊断，再串行运行正式包全链验收，避免并发大下载：

| 对照 | 结果与解释 |
| --- | --- |
| Linux curl：latest 脚本、latest checksum、tagged checksum H1/H2 | 四次失败：三次 TLS 握手超时，一次 TLS 成功且证书校验通过，但 30 秒内没有 HTTP 响应头 |
| Linux curl：匿名 latest API，H2 | HTTP 200，证书校验通过 |
| Go 1.27.2 独立 httptrace：同一 tagged checksum，H1/H2 | 两次均在 TLS 握手阶段约 10 秒超时；未协商出应用协议，也没有 HTTP 响应 |
| 同一 Go 诊断器：匿名 latest API，H2 | HTTP 200，ALPN h2、可信证书链，完整读取响应 |
| Linux VM host 网络模式：单个 checksum H1 | TLS 握手仍超时；该模式共享 OrbStack Linux VM 网络，不代表 macOS 原生路由 |
| Cloudflare、Google 公共 DoH：三个官方域的 A 查询 | TLS 错误或超时，没有取得新的可信解析地址；未猜测 IP、使用 `--insecure` 或写入 hosts |

因此，**当前链路确有独立于 Nido 安装、包解析及替换逻辑的传输故障**。H1 也失败，不能把两场历史故障统一归因于 HTTP/2；API 可用也不能证明发行资产域可用。本次没有证据证明发行资产损坏，或应修改协议、放宽超时或增加重试。

容器仍使用 resolver `0.250.250.200`，三个官方域分别解析到 `198.18.1.34`、`198.18.2.199`、`198.18.7.31`；HTTP(S)/ALL_PROXY 环境变量未设置。`direct` 表示没有 GitHub 加速前缀，不保证底层不存在 TUN 或其他转发。没有获得具体出口切换信息，不能据此宣称已验证另一个物理出口；本次记录的是当前时段的实际恢复/失败及临时网络模式对照。相同 DNS 映射也不能证明背后出口没有变化。

新旧输入分别为独立验签的真实 v0.8.1、v0.8.0，执行前重新核对官方 API 大小、摘要及 URL；宿主 gh 仅核对公开元数据，凭据不传入容器，客户端使用匿名原生请求。安装器实际公网响应必须在执行前与验签输入逐字一致；原生自更新使用自身 metadata/摘要检查，完成后再与独立验签的新程序逐字核对。

Go 每个资源的总预算为 120 秒，安装器 direct 的连接/总预算分别为 10/180 秒；包为 4,130,275 字节，纯正文在 120 秒内读完至少需要约 33.6 KiB/s，连接与重定向还会消耗时间。这是程序明确的适用边界，不能把健康但超过预算的慢链路混称为包损坏。独立正文追踪结果如下（只做诊断，不放宽正式客户端门限）：

独立 Go 诊断器保留相同官方 URL、UA/Accept、证书验证、协议协商及 120 秒总预算，只取一个 archive，不执行载荷。约 1.266 秒收到 HTTP/2 200 和可信证书链，声明长度 4,130,275 字节；正文读取 118.743 秒后，总时限在 120.011 秒终止。实际仅读到 3,799,232 字节（约 92%），错误明确为 `deadline`，摘要不匹配，载荷被拒绝。

正文平均约 31.2 KiB/s，低于在预算内完成所需速度。**当前可复现的是慢速正文下载与客户端总时限不匹配，另有间歇性 TLS/响应头失败**；它解释了本轮安装器在 180 秒预算内通过、原生更新在 120 秒预算下失败的组合。当前还原不能证明所有历史空响应或断流均为同一原因，亦未定位到具体 ISP、转发软件或上游服务。诊断没有放宽正式门限，不把它记为更新通过。

## 本轮源码修复（未发布）

`internal/githubdownload/download.go` 原来把所有请求错误合并为“连接失败或超时”，并抹去响应读取错误原因。现仅按确定的错误类型输出 DNS、TLS、超时、连接中断等固定脱敏类别；保留 `errors.Is/As` 检查原因的能力，不输出原始错误、代理凭据或签名 URL。未知类型仍标为其他传输错误，不用错误文本猜测。多层 `url.Error`、fmt 包装及多错误链中的超时均有回归覆盖。

路由、HTTPS/证书验证、重定向限制、响应大小、协议协商、超时和重试策略不变。该修复改善诊断能力，不声称已修复网络链路，也不把源码构建当作正式旧版本升级成功。

公网验收脚本还补上真实 update 失败后的核查：旧程序、配置、环境和数据的字节及 mode/UID/GID、禁止调用、临时候选残留。失败记录单独写 `complete=false` 和保护检查结果，仍返回原非零状态，不产生整体 PASS。13 个正负受控分支已在无网 Linux amd64 容器通过。

固定 Go 1.27.2 的 `go vet ./...` 通过。最终源码交叉编译后在无外网、只读根、普通 UID 的 Linux amd64 容器完成下载包全量单元测试、真实本地 TLS H1/H2 完整/截断响应、脱敏与回退检查，以及 Nido/Conda CLI 隔离套件。源码构建标识为测试用 `0.0.0`，另检查真实本地连接拒绝后的分类和旧文件保留；这不是新发行版本。未重跑完整 Conda 24.1.2 normal/strict：本轮没有改动 Conda 逻辑，旧正式包矩阵沿用 [发行记录](conda-v0.8.1-release.md)。
