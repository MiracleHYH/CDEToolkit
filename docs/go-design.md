# Nido 轻量单目录设计

Nido: Lightweight Development Environment Manager。当前 main 的 Nido 重构尚未发布；GitHub 已有 latest Release 仍为旧 cdet。本文描述新源码，旧双目录审计仅作为历史记录。

Nido 的定位是开发环境配置助手，加少量内置工具。外部软件保留自身的数据格式、运行方式和更新机制，Nido 仅提供明确的集成；内置组件由 Nido 管理最小生命周期。

## 两种责任，单一软件目录

| 类型 | 组件 | Nido 的责任 | 上游或用户的责任 |
| --- | --- | --- | --- |
| 外部集成 | Codex | 发现和关联 HOME、生成环境、局部代理配置、官方安装更新委托、状态和版本查询 | 程序运行、认证、会话、数据库、插件、daemon 和原渠道安装 |
| 内置组件 | Proxy / 可选 GDS | 固定目录安装、配置定位、显式启停、更新、程序卸载 | 提供有效配置与凭据；显式选择启用 |

只选择一个 Nido 软件目录，默认 `~/.nido`，通过 `NIDO_HOME` 或 `--root` 覆盖。

```text
<Nido>/bin/nido
<Nido>/config.toml
<Nido>/env.sh
<Nido>/proxy/          # 内核、固定 config.yaml、日志与进程记录
<Nido>/gds/            # 可选独立程序、日志与进程记录
<外部 CODEX_HOME>/    # 留在 Nido 目录之外
```

外部 HOME 与 Nido 根不能相互包含。没有独立组件存储根、安装实例与存储实例绑定、路径历史映射或完整目录迁入。Nido 根不是任意项目或实验目录，首次初始化拒绝已有无归属内容。

## 初始化与环境

安装器只下载并校验 Nido，调用 `init` 放置自身程序、配置和环境文件。初始化不自动选择组件，不编辑用户 Shell、不注册或启动服务。生成文件的归属摘要只用于避免覆盖用户改动，不是软件版本仓库或全目录校验。

用户显式 source `env.sh` 后得到 Nido 路径；主动关联 Codex 后再增加 `CODEX_HOME` 和识别到的官方命令目录。没有 Codex 包装器，不介入执行链，不全局配置代理或更改其他 `CODEX_*`。

CLI 无法修改已经存在的父 Shell，因此配置完成后输出重新加载提示；解除关联也不声称已经清除了当前终端里的旧变量。

## 外部 Codex 集成

关联只记住用户选择的 HOME 与已识别命令，不变更原目录。首次发现只检查当前 `CODEX_HOME` 和默认 `~/.codex` 的可用候选，不扫描整盘；显式配置优先。重复关联默认使用已经登记的目录，不随终端环境改变原选择。

Codex HOME 本身作为不透明数据使用。Nido 不读取认证、会话和数据库，不解析配置中的 SQLite 路径，不修补 package/current 或临时链接，不检查或终止全机 Codex 进程。

代理配置只处理 `.env` 的 Nido 标记块，并记录实际写入内容。非受管代理冲突、未知标记、符号链接、并发改动或用户修改受管内容时停止。删除代理配置和解除关联仅移除仍能证明归属的字节，其他内容保留；不 source 或执行用户 `.env`。

代理归属记录必须严格符合本工具生成的块语法，不能作为任意用户内容的删除凭据；硬链接同样拒绝修改。没有代理归属记录时，解除关联仅改变 Nido 配置。进程中的显式空代理值仍覆盖 `.env`，安装和查询使用同一大小写规范；不扩展为完整 dotenv 执行器。

安装与更新委托官方脚本。程序默认安装到外部 `~/.local/bin`；更新已关联 standalone 时沿用原命令目录。安装器以临时 HOME 运行，显式注入 HOME 选择、程序目录、非交互开关和代理；其他应用行为仍归上游。npm、Homebrew 或未知渠道不被静默转成 standalone。

最新版本在显式 `update --check` 或更新确认前查询；普通本地状态只运行受关联程序的 `--version`。不自行实现 Codex 下载替换、版本仓库、回滚或数据兼容处理。

## 内置组件

Proxy、GDS 具有独立固定目录，状态按本地程序、配置和经过核验的进程记录计算。配置不长期保存容易失真的已安装或运行布尔值。

Proxy 默认使用 Mihomo 官方稳定版资产与其摘要；本地程序安装还检查格式、架构和必要依赖边界。用户提供固定 `proxy/config.yaml`，不导入外部 Proxy 环境。

启动、停止都是显式操作。Nido 没有常驻守护进程、自动重启或服务注册；只核验自己记录的精确进程，不按名称批量停止其他服务。

Mihomo 优先使用可核验归属的本地官方更新接口；不适用时，停止状态下校验并原子替换内核。已经提交官方更新后不静默降级到另一条替换路线。更新不会覆盖配置，卸载只移除程序和已停止的进程记录。

GDS 必须显式提供本地程序，不设默认下载源，也不作为 Codex 或 Proxy 的安装依赖。Go 调度启动尚未适配，`start` 明确拒绝，不能将仓库中的 CUDA worker 当作完整空闲调度器运行；可选源码及显式程序安装、更新、删除保留。

## 轻量安全边界

管理操作使用短期互斥锁，必要文件通过临时文件和原子替换写入；配置、环境及代理块在写入前检查归属与并发变更。保留这些局部校验，避免引入通用事务引擎、回滚记录和恢复状态机。

锁文件保持稳定，不在失败时删除。首次初始化在取得锁后再次检查目录内容，配置必须明确包含产品及 schema 身份。配置、环境与自身程序每次覆盖前都复核预期快照，避免长操作结束后覆盖编辑者的新内容。

跨文件写入不是通用 all-or-nothing 事务；不提供外部应用快照、数据备份或上游安装失败回滚。失败时不清空外部 HOME，不递归删除未知数据。

仅对本次代理块修改保留内存中的短期补偿：首次配置提交失败时，原文件仍与本次结果一致才恢复；有并发变化时保留现场并报错。配置已提交、环境文件刷新失败时保留已提交的归属记录，允许重试 `init`，不回放日志或回滚上游程序。

没有目录搬运、挂载恢复、旧路径兼容和任意配置替换。外部路径变化只能通过用户明确选择重新关联，内部数据和外部依赖仍由其所有者处理。

## 组件接入方式

当前使用小型、静态组合，不建设插件框架：

- `internal/nido`：CLI、单根配置、环境和组件组合。
- `internal/integrations/codex`：独立外部集成，通过显式配置与命令执行接口提供功能。
- `internal/builtin`：固定目录、程序更新及最小进程控制；小型静态组件表负责识别和列举，组件特有行为独立实现。
- `internal/distribution`：源码构建、归档与校验，独立于运行时组件逻辑。

新增组件首先确定所有权：外部集成只增加上游公开的配置与安装委托；内置组件增加独立目录、自己的配置检查和程序来源。组件不导入 CLI，不借用 Codex 数据结构，也不要求先安装其他组件。仅在实际重复出现后抽取公共逻辑，不为假想组件增加通用生命周期抽象。

具体验证和构建边界见 [CI 与发行](go-ci-release.md)，日常命令见 [使用指南](usage.md)。
