# Nido 轻量单目录设计

Nido: Lightweight Development Environment Manager。从 v0.3.0 起采用本单目录设计；旧 cdet 与双目录审计仅作为历史记录，不会自动迁入。

Nido 的定位是开发环境配置助手，加少量内置工具。外部软件保留自身的数据格式、运行方式和更新机制，Nido 仅提供明确的集成；内置组件由 Nido 管理最小生命周期。

## 两种责任，单一软件目录

| 类型 | 组件 | Nido 的责任 | 上游或用户的责任 |
| --- | --- | --- | --- |
| 外部集成 | Codex | 发现和关联 HOME、生成环境、局部代理配置、官方安装更新委托、状态和版本查询 | 程序运行、认证、会话、数据库、插件、daemon 和原渠道安装 |
| 外部集成（自 v0.8.0） | Conda / pip | 持久原镜像 default、镜像切换、缓存与环境位置原生配置、静态状态与显式只读验证 | 程序安装和初始化、频道选择、包与环境创建、数据迁移及缓存清理 |
| 内置组件 | Proxy | 原生配置、静态与核心验证、端点导出、精确启停、停止更新、程序卸载 | 节点、规则、provider、连接与核心数据 |
| 可选组件 | GDS | 独立程序配置与启停、UUID 空闲观察、有限许可显存保留 | NVIDIA 驱动与受支持宿主环境；真实 GPU 验收 |

只选择一个 Nido 软件目录，默认 `~/.nido`，通过 `NIDO_HOME` 或 `--root` 覆盖。

```text
<Nido>/bin/nido
<Nido>/config.toml
<Nido>/env.sh
<Nido>/conda/          # v0.8.0 起：确定性内容命名的镜像覆盖文件
<Nido>/proxy/          # 内核、固定 config.yaml、日志与进程记录
<Nido>/gds/            # 可选独立程序、日志与进程记录
<外部 CODEX_HOME>/    # 留在 Nido 目录之外
```

外部 HOME 与 Nido 根不能相互包含。没有独立组件存储根、安装实例与存储实例绑定、路径历史映射或完整目录迁入。Nido 根不是任意项目或实验目录，首次初始化拒绝已有无归属内容。

## 初始化与环境

安装器只下载并校验 Nido，调用 `init` 放置自身程序、配置和环境文件。初始化不自动选择组件，不编辑用户 Shell、不注册或启动服务。生成文件的归属摘要只用于避免覆盖用户改动，不是软件版本仓库或全目录校验。

用户显式 source `env.sh` 后得到 Nido 路径；主动关联 Codex 后再增加 `CODEX_HOME` 和识别到的官方命令目录。没有 Codex 包装器，不介入执行链，不全局配置代理或更改其他 `CODEX_*`。

CLI 无法修改已经存在的父 Shell，因此配置完成后输出重新加载提示；解除关联也不声称已经清除了当前终端里的旧变量。

## GitHub 下载与自身更新

本节能力自 v0.7.0 提供；v0.6.0 及更早版本不包含这些命令与安装器参数。

下载策略独立于组件生命周期：`direct`、`auto` 或一个无认证信息的 HTTPS 加速前缀，保存于主配置的 `[download].github_proxy`。覆盖优先级为命令选项、`NIDO_GITHUB_PROXY`、保存值、默认 `auto`。网络代理与 GitHub URL 前缀是两个独立输入，不相互转换。

`auto` 只对支持的公开 GitHub URL 先尝试官方来源，短超时失败后使用固定、少量的第三方前缀，有界请求而非永久重试。API 只回退到 `gh-proxy.org`，资产才继续使用 `ghfast.top`。自定义前缀拼接完整 GitHub URL；其他域名与 Codex 安装脚本不会被改写。公共下载逻辑不导入组件，组件只传递显式下载选项，不依赖启动其他组件。

短期限限制官方连接和响应头，不中断已开始的正常响应体；总时间和大小仍有界。跳转只允许官方 GitHub/CDN、选定入口和预设已知域名，并逐次拒绝认证查询参数。下载配置按使用范围验证，错误偏好不阻断外部 Codex 或离线管理；修正偏好无需先执行任何网络请求。

POSIX 首装脚本同样支持 `--github-proxy` 和环境变量，并贯通包与摘要下载。首次显式选择交给临时 CLI 的 `init` 保存；没有显式选择时仅本次下载默认 `auto`，不由 Shell 解析或覆盖原有 TOML。压缩下载和解包输出分别设置大小边界，解包超限不执行候选程序。外层脚本 URL 必须由用户选择官方直链或可信第三方，脚本内部的回退无法帮助尚未下载成功的脚本。

`nido update` 只下载、校验并替换当前正在运行的受管 `bin/nido`，不重新初始化组件，不覆盖现有配置和数据。`--check` 查询版本，`--version` 选择明确稳定新版；同版不下载，拒绝降级，`dev` 构建需从源码更新。不建立版本仓库、回滚目录和通用事务引擎。客户端核对包与 SHA-256，但不验证 Sigstore。第三方同时控制包及摘要时，摘要不能证明官方真实性；经第三方下载的首装脚本还具有直接执行的信任边界。

一次更新仅保留内存中的入口身份与字节快照，跨越版本查询和用户确认；不生成事务文件。候选执行前后及原子替换前复核归属，清理也只处理身份仍匹配的自建临时文件。归档和程序同时核验元数据与实际文件格式，不仅信任文件名或 Go 构建参数。

## 外部 Codex 集成

关联只记住用户选择的 HOME 与已识别命令，不变更原目录。首次自动发现按 `CODEX_HOME` → 默认 `~/.codex` → 自定义路径询问的优先链执行，找到首个有效目录就停止；前两项都不可用才询问，不扫描整盘。显式 `--home` 优先，输入无效就报错。重复关联默认使用已经登记的目录，不随终端环境改变原选择。

Codex HOME 本身作为不透明数据使用。Nido 不读取认证、会话和数据库，不解析配置中的 SQLite 路径，不修补 package/current 或临时链接，不检查或终止全机 Codex 进程。

代理配置只处理 `.env` 的 Nido 标记块，并记录实际写入内容。非受管代理冲突、未知标记、符号链接、并发改动或用户修改受管内容时停止。删除代理配置和解除关联仅移除仍能证明归属的字节，其他内容保留；不 source 或执行用户 `.env`。

代理归属记录必须严格符合本工具生成的块语法，不能作为任意用户内容的删除凭据；硬链接同样拒绝修改。没有代理归属记录时，解除关联仅改变 Nido 配置。进程中的显式空代理值仍覆盖 `.env`，安装和查询使用同一大小写规范；不扩展为完整 dotenv 执行器。

安装与更新委托官方脚本。程序默认安装到外部 `~/.local/bin`；更新已关联 standalone 时沿用原命令目录。安装器以临时 HOME 运行，显式注入 HOME 选择、程序目录、非交互开关和代理；其他应用行为仍归上游。npm、Homebrew 或未知渠道不被静默转成 standalone。

最新版本在显式 `update --check` 或更新确认前查询；普通本地状态只运行受关联程序的 `--version`。不自行实现 Codex 下载替换、版本仓库、回滚或数据兼容处理。

## 外部 Conda / pip 集成

本集成自 v0.8.0 提供。实现位于 `internal/integrations/conda`，管理层只组合配置与命令，不把 Conda 当作 Nido 内置程序。`setup [conda|pip|all]` 首次捕获本机原有效镜像为持久 default；第一次直接切换镜像时也自动捕获对应工具，失败不切换，已有快照不覆盖。default、official（别名 conda/pypi）与镜像预设并列；off 释放单项，reset 清空选择但保留 default。

镜像定义写入 Nido 主配置、环境文件和 `<Nido>/conda/mirror-<hash>.yaml`。没有显式文件时通过 overlay 的 `CONDARC` 激活；已有外部 CONDARC 时持久保留原路径，仅在原文件更新七个镜像字段，证书、代理、未知非镜像键继续实时读取，原标准文件去重、变量引用和目标 prefix 优先级不变。预设保留当前频道选择，标准用户文件同步 `channels` 防止早先列表合并。显式 default 将受管标准用户与显式源文件的完整已捕获镜像字段恢复，清除后来新增的映射；旧五字段快照仅恢复已记录字段。off/reset 不回写原生值并保留来源关联。默认输出不泄露快照凭据；所有新复制的镜像凭据均不得传播到他人可读文件。旧镜像资源不递归清理。

缓存和环境目录原地修改 Conda 的 `envs_dirs` / `pkgs_dirs` 及 pip 的 `global.cache-dir`。已选择 Conda 镜像时，原生频道和目录同步标准用户 `.condarc` 与持久关联的原显式 `CONDARC`；任一目标不安全则预检失败，不改不可变 overlay。保留其他键语义、注释、权限与所属组，YAML 格式可能调整；pip 尽量保留非目标行。预览列出实际文件。不设置路径环境覆盖或 `PIP_CONFIG_FILE`，已有覆盖报冲突。目录无需 source，off/reset 只停跟踪，不恢复原生值或搬迁清理数据。

`env.sh` 仅对镜像变量保存加载前值，off/reset 后再次 source 恢复；用户手改的新值保留。它不为 cache/envs 创建环境恢复状态。持久 default 可跨 Shell 和重启重新选择，不依赖这份短期撤销状态；镜像变更不会直接改变父 Shell。

`status` / `show` / `mirrors` 和 init 不执行上游程序。setup、镜像切换和 validate 显式调用本地 Conda 与 `python -m pip` 做只读查询，不联网、不安装；validate 不向子进程注入尚未 source 的镜像。检查覆盖原生目录、实际镜像与额外 index 等因素。详细语义、预设来源和隔离测试见 [Conda 设计](conda-design.md)。

## 内置组件

Proxy 实现集中在 `internal/components/proxy`。它拥有独立固定目录、原生 `config.yaml` 和受管进程记录，不导入 `internal/nido` 或 Codex，也不沿用旧 `internal/builtin` 的 Proxy 适配。主配置是唯一配置事实来源，Nido 的 `config.toml` 不复制端口或订阅。

Proxy 使用 Mihomo 官方稳定版资产或显式本地程序，检查摘要、平台格式和候选版本。`configure` 接收隐藏输入的 provider URL 或私有 YAML 文件，静态与核心验证后原子保存，不导入外部服务和缓存。静态策略只允许受支持的回环 HTTP/SOCKS 入口，未知节点与路由语义仍由核心解释；文件检查不构成 OS 沙箱。

本地状态分别表达程序、静态配置、运行阶段、监听归属及配置变更。普通 `status` 不执行核心验证或联网，`endpoint` 返回结构化配置快照；`validate` 和 `probe --url` 分别显式执行核心检查与目标网络测试。监听就绪不等于远端节点可用。

启动使用一次性管道握手，先提交 PID、用户、系统启动标识和结构化出生信息，再授权启动器 exec 核心；有限等待核验全部导出监听。Linux 使用 `/proc`，可用时通过 pidfd 发送信号；macOS 出生信息来自内核，监听归属通过 `lsof` 核验。身份不明、停止超时或未就绪时保留可解释的记录，不把失败当成停止成功。

启动、停止与 restart 均为显式操作，没有常驻 Nido daemon、自动重启或服务注册。restart 在停止旧进程前验证候选配置。安装和配置不启动组件；更新只接受停止状态，候选程序和配置预检后原子替换，完成后仍停止。Nido 不调用 controller 热更新、不实现 reload，也不清理 `meta-backup`、`meta-update` 或未知数据。卸载仅移除程序，保留配置和运行历史。

Codex builtin 代理只在组合层获取 Proxy 默认端点，再调用 Codex 自己的代理块写入接口。它不启动 Proxy，Proxy 也不主动修改外部 HOME。两个组件没有生命周期依赖。

GDS 使用独立 `gds` 程序，源码位于 `internal/components/gds`、`internal/gdsruntime` 和 `cmd/gds`。管理层保持纯 Go，Linux amd64 的 NVIDIA 适配单独启用 cgo，使用 NVML 与 CUDA Driver API。显存 worker 通过私有管道接受绝对单调期限的有限许可，失去有效观察即释放；Nido 不修改 Codex 的全局规则。自 Nido v0.5.0 接入独立 gds-v 标签的官方资产发现、摘要校验与本地程序两种来源，不作为其他组件依赖；安装更新不启动。真实 GPU 验收尚未完成，详见 [GDS 设计](gds-design.md) 与 [独立发行](gds-release.md)。

## 轻量安全边界

管理操作使用短期互斥锁，必要文件通过临时文件和原子替换写入；配置、环境及代理块在写入前检查归属与并发变更。保留这些局部校验，避免引入通用事务引擎、回滚记录和恢复状态机。

锁文件保持稳定，不在失败时删除。首次初始化在取得锁后再次检查目录内容，配置必须明确包含产品及 schema 身份。配置、环境与自身程序每次覆盖前都复核预期快照，避免长操作结束后覆盖编辑者的新内容。

跨文件写入不是通用 all-or-nothing 事务；不提供外部应用快照、数据备份或上游安装失败回滚。失败时不清空外部 HOME，不递归删除未知数据。

仅对本次代理块修改保留内存中的短期补偿：首次配置提交失败时，原文件仍与本次结果一致才恢复；有并发变化时保留现场并报错。配置已提交、环境文件刷新失败时保留已提交的归属记录，允许重试 `init`，不回放日志或回滚上游程序。

没有目录搬运、挂载恢复、旧路径兼容和任意配置替换。外部路径变化只能通过用户明确选择重新关联，内部数据和外部依赖仍由其所有者处理。

## 组件接入方式

当前使用小型、静态组合，不建设插件框架：

- `internal/nido`：CLI、单根配置、环境和组件组合。
- `internal/integrations/codex`：独立外部集成，通过显式配置与命令执行接口提供功能。
- `internal/integrations/conda`：自 v0.8.0 提供的 Conda / pip 配置、镜像覆盖与只读核对，不管理上游程序生命周期。
- `internal/components/proxy`：独立 Proxy 的配置、端点、程序来源、进程和平台实现。
- `internal/components/gds`：可选 GDS 的程序、配置和管理接口；旧 `internal/builtin` 已退出。
- `internal/gdsapi`、`internal/gdsutil`、`internal/gdsruntime`：GDS 的协议、局部文件与进程保护、状态机及运行程序。
- `internal/distribution`：源码构建、归档与校验，独立于运行时组件逻辑。

新增组件首先确定所有权：外部集成只增加上游公开的配置与安装委托；内置组件增加独立目录、自己的配置检查和程序来源。组件不导入 CLI，不借用 Codex 数据结构，也不要求先安装其他组件。仅在实际重复出现后抽取公共逻辑，不为假想组件增加通用生命周期抽象。

Proxy 细节与限制见[组件说明](proxy-design.md)。源码审计、假核心和辅助进程回归，以及此前授权的临时 HOME 真实 Mihomo 验证，分别记录在[Proxy 审计记录](proxy-audit.md)；各平台的原生、race 和交叉编译范围不能互相替代。独立 Proxy 自 v0.4.0 提供，服务器验收目标为 Linux amd64，安装不切换实际组件入口。构建边界见 [CI 与发行](go-ci-release.md)，日常命令见 [使用指南](usage.md)。
